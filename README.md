# INCUVA Data Platform API

## Local setup

Run these commands from `backend/` after activating the project's Python environment. Development and production require PostgreSQL through `DATABASE_URL`; SQLite is used only by the automated test configuration.

```powershell
$env:FLASK_APP = "run.py"
$env:FLASK_ENV = "development"
pip install -r requirements.txt
flask db upgrade
flask create-org
flask create-user
python run.py
```

`flask db upgrade` creates or upgrades the schema using versioned migrations in `migrations/`. `create-org` prints the organization ID to use when `create-user` prompts for it. User passwords must contain at least 12 characters. The CLI creates password hashes; it never stores the plaintext password. Login returns a 15-minute access token and a 14-day refresh token. The `/v1/auth/me` endpoint validates the current user and organization; logout revokes the whole session in PostgreSQL. Set `JWT_SECRET_KEY` to a random value of at least 32 characters before starting the backend; placeholder and missing values are rejected.

### Database migrations

Migration `64275f79d812` establishes the original 19 application tables. Later migrations add integration, HR data contract and governance support. The current schema includes `agentic_action_proposals` in addition to the existing organization, user, employee, onboarding, integration and governance tables. Alembic also creates `alembic_version` to record the applied revision. Tests use SQLite; development and production use PostgreSQL via `DATABASE_URL`.

For a new empty database, run `flask db upgrade`. For later code changes, generate a candidate migration with `flask db migrate -m "describe the schema change"`, review the generated file in `migrations/versions/`, then apply it with `flask db upgrade`. Autogenerated migrations are proposals: check table names, data types, constraints, indexes, and both `upgrade()` and `downgrade()` before applying them. Do not edit an already-applied migration; add a new revision instead.

To adopt an existing database created by the former `upgrade-*-schema` commands, first make and verify a PostgreSQL backup. `flask db check` requires the database to already be at the latest migration revision, so it cannot be used before the baseline is stamped. Before stamping, compare the existing tables, columns, types, constraints, and indexes with migration `64275f79d812` (or do this first on a restored backup in a staging database). If they match, run `flask db stamp 64275f79d812`, then `flask db current` and `flask db check`. `stamp` only records the version; it does not create, alter, or delete application tables or rows. Never run `flask db upgrade` against an unversioned existing schema before stamping: the initial migration would try to create tables that are already there. If the schema is not an exact match, do not stamp it as the baseline; reconcile the differences with a reviewed migration on a backup/staging copy first.

The old `flask upgrade-meeting-schema`, `flask upgrade-onboarding-schema`, `flask upgrade-integration-schema`, and `flask upgrade-governance-schema` commands have been retired. Use the migration workflow for all schema changes.

## Onboarding

- `GET /v1/onboarding/plans` lists the authenticated organization's onboarding plans.
- `POST /v1/onboarding/plans` creates a plan for an existing employee and proposes editable steps based on the role and start date.
- `GET /v1/onboarding/plans/<id>` returns one organization-scoped plan.
- `POST /v1/onboarding/plans/<id>/tasks` adds a custom task; `PATCH /v1/onboarding/tasks/<id>` updates a task to `pending`, `in_progress`, or `completed`.

The initial planner is deterministic and does not call a paid or hosted model. Mobyus suggestions are starting points for the HR team to review and adapt.

Mobyus uses a local Hugging Face model by default, so no API key is needed. The first analysis downloads the configured model and runs it on the available CPU or CUDA GPU. Set `LLM_PROVIDER=anthropic` and provide `ANTHROPIC_API_KEY` to use Anthropic instead.

The local model is configured with `HF_MODEL_ID` (default: `Qwen/Qwen2.5-1.5B-Instruct`). Model weights are downloaded from Hugging Face on the first analysis and cached locally.

The frontend currently calls the API at `http://localhost:5000`.

## Risk signal import

Risk detection can be populated through a validated CSV import into INCUVA's PostgreSQL database. See [`RISK_SIGNAL_IMPORT.md`](RISK_SIGNAL_IMPORT.md) for the template, preview command, and import command. The import is scoped to one INCUVA organization and uses only known indicator keys.

## Webhook verification

Webhook endpoints fail closed with `503` until their verification secrets are configured. Set `TEAMS_WEBHOOK_CLIENT_STATE` to a random value of at least 32 characters and configure the same value as the Microsoft Graph subscription `clientState`. Set `ZOOM_WEBHOOK_SECRET_TOKEN` to the Secret Token configured for the Zoom webhook. Zoom signatures are checked against the raw request body and timestamps older than five minutes are rejected. Keep these values private and restart Flask after changing them.

Generate URL-safe random values in PowerShell with:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Microsoft Graph's `validationToken` handshake is echoed as plain text. Zoom's `endpoint.url_validation` handshake is answered with the HMAC-SHA256 token required by Zoom.

## Integration credential storage

The Workspace integrations page saves organization-scoped credentials through authenticated `GET /v1/integrations`, `PUT /v1/integrations/<key>/credentials`, and `DELETE /v1/integrations/<key>/credentials` endpoints. Credential values are encrypted with Fernet before being stored in PostgreSQL and are never included in API responses.

### BambooHR employee sync

BambooHR is the first complete read-only HRIS connector. `POST /v1/integrations/bamboohr/test` checks the saved API key against the employee-list endpoint. `POST /v1/integrations/bamboohr/sync` queues a full roster import; `GET /v1/integrations/bamboohr/sync` returns the organization-scoped status, count, last success, and sanitized error. Start a Redis service matching `REDIS_URL` and `CELERY_BROKER_URL`, then run a worker from `backend/` (Windows development):

```powershell
celery -A run:celery worker --loglevel=info --pool=solo
```

The connector uses BambooHR's cursor pagination, requests names and basic organizational fields only, retries transient network/HTTP failures, and maps BambooHR's stable employee ID to an INCUVA employee inside the same organization. Re-running a full import updates those mapped rows instead of duplicating them. A failed run can be retried from the Integrations page; already committed pages remain and are safely upserted on retry. Employees missing from a later source response are not automatically deleted or deactivated. The API key inherits the BambooHR user's read permissions, so use a dedicated least-privilege account. Newly added tables require `flask db upgrade` before starting syncs.

Install the new dependency from `backend/` with `pip install -r requirements.txt`, then set `INTEGRATION_CREDENTIALS_KEY` in `backend/.env`. Generate a key with:

```powershell
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

The `integration_credentials` table is created by the initial migration. Keep the encryption key backed up and private. To rotate it without losing stored credentials, set the new key as `INTEGRATION_CREDENTIALS_KEY`, the previous key in `INTEGRATION_CREDENTIALS_FALLBACK_KEYS`, then run `flask rotate-credential-encryption-key`; remove the fallback key after verifying the rotation.

## Governance foundation

The initial migration creates the organization-scoped governance tables. The first API surface is protected for organization admins and owners:

- `GET /v1/governance/audit-events` reads the append-only audit trail (`limit` and `before_id` support pagination).
- `GET /v1/governance/secrets` lists secret metadata; `PUT/DELETE /v1/governance/secrets/<name>` creates, rotates, or deletes a secret. Values are write-only over HTTP; backend code can retrieve them with `app.governance.secrets.read_secret`.
- `GET /v1/governance/access-rules` lists rules; `POST /v1/governance/access-rules` creates or updates one; `DELETE /v1/governance/access-rules/<id>` removes it. Explicit deny wins; absent rules use limited viewer, analyst, and manager defaults, while admins/owners retain administration access. `app.governance.access.access_allowed` is the shared enforcement helper.
- `GET/POST /v1/governance/users` lists organization members and creates a login account in the authenticated organization; `PATCH /v1/governance/users/<id>/role` changes a member role and revokes their active sessions. Only organization admins can manage members; owner accounts cannot be changed here.
- `GET/POST/PATCH /v1/governance/budgets` manages daily or monthly limits by organization, model, or user. `app.governance.budgets.consume_budget` reserves caller-estimated usage before a billable operation; a request key makes retries idempotent. Reconciliation against provider-reported actual usage and refunds are not implemented yet.
- `GET/PUT /v1/governance/controls` configures `action_allowlist`, `export_row_limit`, and `require_approval` controls. `app.governance.controls.evaluate_control` evaluates them and writes the result to the audit trail.

Audit details are recursively redacted for secret-like field names. The audit API exposes no update/delete operation, and SQLAlchemy rejects mutation/deletion of audit rows. Approval requests are organization-scoped, cannot be approved by their requester, and are consumed once. `meeting.analyze` and integration credential save/delete can be gated by a `require_approval` control. Set its `actions` list to the exact action keys to require a review. Approval should be used for operations with business impact; model output itself never authorizes an operation.

Access rules are enforced on employee, risk, meeting, onboarding, and integration endpoints. Meeting analyses can consume an organization budget configured with meter `llm_requests` and unit `REQUESTS`; cost budgets can be recorded by services through `consume_budget`. New viewer, analyst, and manager accounts receive limited role defaults; organization admins can refine exact resource/action permissions from the dashboard. Role changes are resolved from PostgreSQL and revoke old sessions so stale JWT claims do not retain access.

## Agentic action proposals (A3.1)

The internal action proposal engine accepts only the explicitly registered, proposable write contracts. It validates and previews proposals, encrypts their normalized snapshot, seals its metadata with a separate HMAC key, and persists it without executing any employee or onboarding mutation. The API is `POST /v1/agentic/proposals`, `GET /v1/agentic/proposals/<proposal_id>`, and `POST /v1/agentic/proposals/<proposal_id>/cancel`. Proposal reads and cancellation are restricted to the initiating user and organization. There is deliberately no confirmation or execution endpoint in A3.1.

Configure independent base64-encoded 32-byte keys and distinct key IDs: `AGENTIC_PROPOSAL_ENCRYPTION_KEY_ID`, `AGENTIC_PROPOSAL_ENCRYPTION_KEY`, `AGENTIC_PROPOSAL_HMAC_KEY_ID`, and `AGENTIC_PROPOSAL_HMAC_KEY`. Fallback keys use comma-separated `key-id=base64-key` entries in `AGENTIC_PROPOSAL_ENCRYPTION_FALLBACK_KEYS` and `AGENTIC_PROPOSAL_HMAC_FALLBACK_KEYS`; retain old keys until all proposals sealed with them have expired and passed the retention window. The service fails closed for proposal creation/inspection when required keys are absent or malformed; do not reuse JWT or integration keys. `AGENTIC_PROPOSAL_TTL_SECONDS` defaults to 900 and accepts 60–3600 seconds.

`incuva-json-subset-v1` is versioned deterministic UTF-8 JSON: values may be null, booleans, strings, safe integers (absolute value at most 2^53−1), arrays, and objects with string keys. Object keys are sorted by Unicode code point; separators contain no optional whitespace; Unicode is emitted directly without NFC/NFD normalization; dates must first be normalized by capability validation to ISO strings. Floats (including non-finite values), decimals, datetime/date objects, bytes, non-string object keys, unsafe integers, and unsupported Python values are rejected. Thus `true` and `1` remain distinct, and canonically equivalent Unicode spellings remain distinct strings. Optional fields are represented according to the validated contract's normalized model dump; unknown fields are rejected by contract validation. Any future representation change requires a new canonicalization version and reader support for existing rows.

On initial creation, a 256-bit random token is returned. Its digest remains in the proposal record, and a temporary AES-GCM encrypted recovery copy is stored under a third, independent key. A retry with the same authenticated user, organization, idempotency key, and action may recover the same token while the proposal is pending and unexpired. A normal GET never returns it. The server clock invalidates recovery as soon as the deadline passes; lazy expiration and the bounded sweep clear the encrypted copy, as does cancellation. Terminal proposals cannot recover tokens. Proposals created before this recovery migration have no recovery copy and remain readable, but their tokens cannot be recovered. Expiration is enforced during reads, cancellation and idempotency replay; `ActionProposalService.expire_due()` supports a bounded sweep, but no periodic Celery Beat schedule is configured. Proposal rows and encrypted payloads currently have no automatic retention purge; define and deploy a retention policy before production use.

Token recovery requires `AGENTIC_PROPOSAL_RECOVERY_KEY_ID` and `AGENTIC_PROPOSAL_RECOVERY_KEY`; old recovery keys use `AGENTIC_PROPOSAL_RECOVERY_FALLBACK_KEYS` as comma-separated `key-id=base64-key` entries. Recovery, payload-encryption and HMAC keys must all be independent. Keep fallback keys while retained records reference them. To revoke a compromised key, remove its ID from active and fallback configuration; affected ciphertext then fails closed and cannot be recovered or decrypted. The recovery key has no default and tests configure a generated key explicitly.

## Security operations

- Tenant ownership is taken from the authenticated session and applied to database queries. Do not accept an organization ID supplied by a browser as authority. Cross-organization denial tests cover employees, meetings, onboarding plans, integration credentials/secrets, access rules, approvals and retention purge.
- Integration credentials and governance secret values are Fernet-encrypted in PostgreSQL. OAuth app credentials are scoped to an INCUVA organization. Current connectors use application credentials, so the provider sees the integration's granted application scopes; delegated per-user source permissions and automatic per-record ACL mirroring are not implemented. Grant only the minimum provider scopes required and treat imported data as visible to authorized members of the connected INCUVA organization.
- Production startup requires HTTPS origins, PostgreSQL `sslmode=require` or stronger, and `rediss://` Redis/Celery URLs. Configure the reverse proxy for TLS and set `TRUSTED_PROXY_COUNT` to the exact trusted proxy count. Production rejects requests not marked secure. PostgreSQL table data (including transcripts and employee records) is not field-encrypted by this application: enable encrypted database volumes/storage and encrypted managed snapshots at the hosting layer, protect keys separately, and test restore procedures.
- API rate limits are shared through Redis in production and fail closed if Redis is unavailable. Development/tests use an in-process fallback. Model request budgets are reserved before meeting analysis; configure organization budgets using meter `llm_requests` (unit `REQUESTS`). Provider cost reconciliation is not implemented, so this controls request volume rather than an exact invoice amount.
- Prompts treat transcripts as untrusted data and constrain model output. Model responses are proposals; no general-purpose tool/action executor is exposed. Sensitive analysis and credential changes can require an explicit human approval as described above. Do not add automatic execution of model-generated instructions without a separate authorization and review path.
- Retention defaults to no automatic deletion until an organization configures its policy. Admins can use `GET/PUT /v1/governance/retention-policy` with day counts (or `null` to retain indefinitely). Schedule a preview regularly with `flask purge-expired-data`; inspect the counts, then pass `--commit` to delete expired meetings, signals, risk scores, insights and completed onboarding plans. The command supports `--org-id` to scope a run. Audit events, users, employees and active onboarding plans are deliberately not purged by this command and require a separately approved legal/operational policy.

### PostgreSQL backup and restore

The scripts in `scripts/` create a `pg_dump` custom-format backup and encrypt it with GPG for a configured recipient. Set `PGHOST`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, and `INCUVA_BACKUP_RECIPIENT`, then run `./scripts/backup-postgres.ps1`. Store the GPG private key and Fernet key in a separate protected key store; never put them beside the backups. Restore only into a separate empty staging database first: configure the `PG*` variables for staging and run `./scripts/restore-postgres.ps1 -BackupFile <encrypted-backup>`. Verify application login, tenant isolation and representative records before planning a production cutover. Schedule backups and periodically rehearse restores; the scripts do not provision encrypted storage or create a schedule themselves.

### Secret exposure response

Never commit `.env`, provider credential JSON, database passwords or signing/encryption keys. If any were committed, revoke and replace them at their issuing providers, update local/deployment secrets, and remove them from Git history before publishing the repository. Removing a file from the current index does not erase earlier commits or copies already cloned.

## Meeting Intelligence v1

- `POST /v1/meeting-analyze` accepts `{ "title": "...", "transcript": "..." }`, runs Mobyus extraction and stores the transcript, decisions, actions and participants.
- `GET /v1/meetings` lists up to 100 meetings belonging to the authenticated user's organization.
- `GET /v1/meetings/<id>` returns a meeting from that organization only.
- `PATCH /v1/meetings/<id>/review` accepts `{ "reviewed": true|false }` and records who reviewed it.

Mobyus output is treated as a proposal; a human must review it before sharing or acting on it. Transcripts are retained with the meeting record until the organization's retention policy expires them or an administrator deletes them.
